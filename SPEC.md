# EnsembleKV storage behavior

EnsembleKV is a Go library for storing byte-string keys and values in local databases and distributing them among backing stores. The command in `tool/` opens a selected store to set a value or inspect a key's available history. The library has no graphical interface.

## Public operations

`KvLike` provides `Get`, `Put`, `Exists`, `Delete`, `Size`, `Flush`, `Close`, `Keys`, `MapFunc`, `MapPrefixFunc`, `DumpIndex`, and `KeyHistory`. A creator receives a directory, block size, and file-size setting and returns a store or an error. Managers receive another creator for their backing stores.

- `Get` returns the current value or an error. Missing or deleted keys return an error matching `ErrKeyNotFound`; storage errors retain their original cause. `Put` replaces the current value when the selected backend supports replacement. NuDB is insert-only and returns its duplicate-key error for an attempted overwrite.
- `Delete` makes a key absent. Treatment of already absent keys varies by backend. Empty keys are rejected by BoltDB, Extent, and SingleFileLSM. SingleFileLSM uses a nil value as a deletion marker; a non-nil empty value remains a value.
- `Keys` returns current live keys. Manager bookkeeping prefixes and deletion records are not user keys.
- Iteration calls the callback with keys and values and returns a map describing visited keys. A false map value denotes a deletion record when exposed by that implementation. Callback errors stop iteration and are returned to the caller.
- Prefix matching compares the literal bytes of the prefix. Case, SQL wildcard characters, zero bytes, and non-UTF-8 bytes have no special meaning.
- Iteration permits callback writes. It does not promise a transactional snapshot across concurrent modifications. Returned BoltDB iteration values and JsonKV values do not reference mutable database storage.
- `Flush` completes the selected backend's persistence operation and reports errors. `Close` releases storage resources. Errors must not be interpreted as successful persistence.
- `StoreMetrics` provides `Count() (int64, error)` for distinct live keys and `SizeBytes() (int64, error)` for the total bytes in their current keys and values. Deleted records, older versions, manager prefixes, metadata, and reserved file capacity are excluded. `StoreCount` and `StoreSizeBytes` use those methods when provided and checked streaming enumeration otherwise. Errors are returned rather than reported as zero. Concurrent changes are not a transactional snapshot across all shards. `Size` retains its historical backend-dependent behavior for compatibility; managers use explicit byte measurements for thresholds.
- History is backend-dependent and is not a general versioned-read guarantee. Some adapters implement only the latest value or no history. NuDB, Pudge, and S3 do not implement `Keys` and cannot be used in operations requiring that method.

## Ensemble manager

An Ensemble store has a fixed number of substores. A key hash modulo that count determines its substore. The directory contains `metadata.json` with generation, substore count, and total-key bookkeeping, and a generation directory containing numbered substore directories. Reopening recomputes the count from the authoritative substores instead of trusting a possibly stale metadata count. Metadata publication synchronizes a temporary file, renames it, and synchronizes the directory.

Mutations inspect key presence before and after the backing operation under the substore lock. Inserting a new live key increments the count, replacing a value leaves it unchanged, and removing a live key decrements it. Repeated deletion and backend-specific nil deletion follow the actual stored state. If an operation changes memory before returning a persistence error, the count reflects that change while the error is returned. If the final key state cannot be read, `Count` reports that the count is unknown until reopening. Flush and Close save current bookkeeping; startup recount also covers interruptions before metadata publication.

Operations on one substore are serialized. Explicit flushing visits the substores, and a background worker periodically flushes stores marked dirty using the same substore locks. Close waits for compaction, stops the worker, and closes the active substores. Requests check the lifecycle state after acquiring their substore lock.

Compaction processes substores sequentially. Each attempt creates a fresh sibling `.compacting` directory and a disposable `.compaction-keys` directory. It enumerates the source into a disk-backed key index while registering the replacement, then copies keys under the substore lock. Successful reads of empty values remain empty values. Writes during copying update both stores; deletions are recorded in the disk index so an uncopied key cannot reappear. A source, scratch-index, or replacement mutation failure invalidates the attempt. Enumeration, read, flush, close, filesystem, and reopen errors are returned rather than interpreted as missing keys or successful persistence.

Publication holds the substore lock. Both stores are flushed and closed, and their files and directories are synchronized. A sibling `.compaction` file containing `ensemble-compaction-v1` followed by a newline is synchronized before the first rename. The original directory becomes `.old`, the replacement becomes the primary, and the replacement is reopened and its live-key set checked against the final source state. Renaming `.old` to `.retired` and synchronizing the containing directory commits the replacement before requests resume. Cleanup removes `.retired`, synchronizes that removal, then removes the version marker. A failed rollback or uncertain commit synchronization makes the substore unavailable until it is closed and reopened; operations must not acknowledge writes against an uncertain recovery state.

At startup, a valid version marker makes `.old` authoritative for an unfinished swap. Without a marker, `.old` can be restored when no primary exists; simultaneous primary and backup from an older library are ambiguous and are preserved with an error. Empty unused directories before initial metadata creation are cleaned up as bootstrap artifacts. `.retired` means the primary was committed; the primary must exist and validate before the backup is removed. Recovery checks the existing local storage layout before invoking a creator, so missing files cannot silently become a new empty database. Conflicting backup states, invalid markers, a lone `.compacting` directory, or invalid authoritative data cause an error. A stale `.compacting` directory beside an authoritative source is discarded. Recovery relies on the filesystem honoring file and directory synchronization; the suite exercises persisted directory states and actual local I/O errors, not power-loss behavior of storage hardware.

Compaction uses checked streaming enumeration for supported local backends and recursively for Ensemble, LineLSM, TreeLSM, and StarLSM. Incomplete child sets are rejected. Custom backing stores must provide `KeyRecordStreamer`, whose `StreamKeyRecords` method receives a callback accepting key bytes and a live/deleted flag. Records arrive oldest to newest; the final record for a key decides its presence. Key memory need only remain valid during the callback, and callback errors stop enumeration. The previous array-returning `KeysWithError` capability does not satisfy this bounded-memory contract. Interrupted recovery additionally requires a recognized local storage layout. The existing `KvLike` interface is unchanged. Ensemble requires count support or streaming enumeration at startup, and custom missing-key errors must match `ErrKeyNotFound`.

Enumeration resolves duplicate keys and tombstones on disk. Scratch transactions contain at most 128 records or approximately 1 MiB of key payload, with a single larger key allowed. Hashes locate full keys; full-byte comparisons resolve collisions, and long storage keys are not constrained by the scratch index's own key-length limit. Copy cursors release scratch read transactions before writes can grow that index. Replacement validation compares the exact final live-key membership and count. MegaPool traversal also keeps its queue and visited-node tracking on disk. SingleFile table and record checksums use fixed-size buffers. Additional enumeration memory depends on the largest key and fixed transaction buffers, not the number of keys or table size; copying can allocate the largest value, and each backend retains its own normal caches and buffers. JSON, for example, still loads and serializes its whole store.

Temporary disk space must accommodate a full replacement and scratch key indexes. Ordinary completion and errors release scratch files; startup removes abandoned `.compaction-keys` beside the recovered source. Temporary indexes used for standalone enumeration are disposable. Compaction preserves current values and deletions, not historical values. Each completed substore remains compacted if a later substore fails.

## LineLSM

LineLSM uses four ordered tiers. Lower tiers are newer. Backing keys have `d:` prefixes for data and `t:` prefixes for deletion markers; user keys may themselves contain either prefix. Deletion markers have a non-empty value so backends interpreting nil as deletion retain them.

Lookup examines tiers from newest to oldest and stops at the first value or deletion marker. A newer value is not hidden by an older deletion. Merging a value removes an older destination deletion marker. Public enumeration resolves this same ordering and returns logical keys exactly once.

The directory contains `metadata.json` and backing-store directories named `tier-<level>-store-<identifier>`. Metadata records `tiers`, `max_tier_sizes`, and `last_flush`; each tier contains `level`, `store_ids`, and `total_size`. Store IDs are directory basenames. Reopening uses the listed IDs and rejects missing or invalid referenced stores. Existing store directories with absent or empty tier metadata are ambiguous and are rejected rather than silently opened as an empty database.

Metadata replacement writes and synchronizes a temporary file before renaming it and synchronizing the directory. Flush merges through the tiers and flushes the surviving backing stores. Tier thresholds measure the live bytes in backing records, including their data/deletion prefixes, independently of reserved capacity. Public metrics exclude those prefixes and resolve all tiers. The existing `maxKeys` constructor setting does not impose a separate key-count flush limit.

## TreeLSM and StarLSM

These managers partition a store into sixteen child stores using successive hexadecimal hash characters. Once a split completes, children own lookup, mutation, and enumeration. Old parent copies do not make deleted keys reappear. A missing-key lookup never recurses back into its parent.

TreeLSM child directories use `substore_` followed by the hexadecimal encoding of the complete ASCII hash prefix. Loading verifies that prefix against the persisted ancestry. StarLSM child directory names are single lowercase hexadecimal characters; the full prefix and depth are reconstructed from ancestry. Both managers reopen nested children and enumerate leaf data. Split thresholds use projected live key/value bytes, subtracting the old value for an overwrite. A single oversized record does not trigger repeated empty splits, and no split exceeds the sixteen-character hash depth.

A split first validates, flushes, and synchronizes the authoritative `current` store. Validation uses disposable `.split.check` scratch storage, reclaimed on reopening. Its sixteen children are built under `.split.pending`, with `layout.json` containing version 1, manager kind, complete prefix, and depth. Copying streams live records; children are flushed and closed and the entire pending tree is synchronized. Renaming `.split.pending` to `.split` publishes all children together. The parent directory must be synchronized before child mutations can be acknowledged. Children are reopened at their committed paths; any uncertain publication or reopen failure disables the manager until reopening.

On reopening, `.split.pending` alone leaves `current` authoritative and can be discarded on retry. A valid `.split` requires the exact manifest and all sixteen existing child layouts; committed children are authoritative, including their later writes and deletions. Missing source or child files are rejected before a creator can initialize them. Legacy direct child directories have no durable completion record and are rejected without guessing whether the parent or children contain later changes. This includes complete-looking legacy child sets, which cannot distinguish an interrupted copy from a later deletion.

## Extent

Each store uses `keys.dat`, `values.dat`, `keys.index`, and `values.index`. Both indexes contain signed big-endian 64-bit boundaries beginning at zero. Their corresponding records must have the same count. A negative starting boundary marks a deletion; the magnitude is the byte position. Ending-boundary signs do not change the preceding record's value. Repeated value boundaries represent empty values.

Reopening validates the initial boundaries and finds the common complete record prefix. Trailing partial index entries, unpaired records, or entries extending beyond available data are discarded together with their incomplete data suffixes. Recovery never extends a data file to invent missing bytes. Invalid or missing initial indexes for an existing store are rejected.

Index caching changes lookup cost, not accepted operations or results. Deleted and negatively cached missing keys are excluded from enumeration. Cache replacement and access are synchronized with mutations. Iteration releases storage locks before calling user code and propagates callback failures. Flush reports errors from every data and index synchronization.

## SingleFileLSM

The file begins with a 4096-byte header reservation, followed by a reserved write-ahead-log region and appended sorted tables and table indexes. Version 2 divides the reservation into two 2048-byte header slots. Each slot records magic, version, WAL start, table-region boundary, current index position, table count, a legacy checksum, generation, and a generation checksum. Integers retain the existing little-endian widths: magic/version/checksums/table count are 32 bits and offsets/generation are 64 bits. The generation checksum covers bytes 0 through 35 followed by bytes 40 through 47; excluding the legacy checksum at bytes 36 through 39 avoids CRC cancellation. WAL entries encode checksum, key length, value length, flags, key bytes, and value bytes; a value length of minus one denotes deletion. Keys contain 1 through 1 GiB of bytes and values may contain up to 1 TiB, subject to available resources.

Each append fits entirely inside its WAL reservation. If necessary, pending entries are flushed, and a larger reservation is appended without overwriting existing tables. A durable end marker and payload are written before an entry header makes the entry visible to recovery. Recovery retains the append position of recovered records.

Flushing appends a new table and replacement index after existing data, synchronizes it, then publishes a new header generation to the inactive slot and synchronizes that slot. The other slot is then updated and synchronized before the old WAL may be invalidated or reused. Older table indexes remain intact until replacement metadata is published. A publication or WAL invalidation error disables subsequent writes until reopening. Enumeration resolves latest records over older records, with the memory table taking precedence. Compaction additionally checks the published table count, table checksums, and individual table records and rejects incomplete or corrupt enumeration.

Reopening selects the highest valid header generation and rejects conflicting contents with equal generations. It repairs missing, invalid, or older copies before allowing writes. Version-1 files are upgraded by publishing the second slot before replacing the original header, retaining existing WAL and table offsets. Older readers do not understand version 2. Recovery tolerates an interrupted individual header write; it does not repair corruption affecting both copies, overwritten data from older implementations, or storage hardware that does not honor synchronization.

## JsonKV

`store.json` is an array of objects containing `key` and `value` byte strings, encoded as base64 by JSON. Entries are saved in byte-key order. This preserves arbitrary binary keys without UTF-8 replacement or collisions. Duplicate keys in the array and a null store are rejected.

The previous JSON object format, with text keys and base64 values, remains readable. Subsequent saves use the array format; older library versions cannot read this new format. Saving synchronizes a temporary file, replaces `store.json` by rename, and synchronizes the containing directory. Existing file permissions are preserved; a new store file is private to its owner.

## Other backends and validation

MmapSingleKV stores append-only records in `data.log`. Flush synchronously writes the entire used mapped region and synchronizes the file. SQLite uses `kv.sqlite` with the `kv_store` table and WAL journaling. BoltDB uses `bolt.db` and the `Blocks` bucket; transaction errors are propagated. MegaPool, NuDB, Pudge, and S3 retain their existing storage formats.

The regression suite uses real local backing stores and filesystem operations. It covers persistence, interrupted writes, key enumeration, deletion and reinsertion, binary prefixes and keys, callback mutation, storage errors, and race detection. Remote services are not required.
